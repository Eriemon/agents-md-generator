# Script Guide

All scripts use Python standard library only.

Governance runtime split:
- `agents-md-generator` 自己的治理脚本属于 skill runtime。owner repo 可以继续用 `python skills/agents-md-generator/scripts/...` 自举；普通外部工作区生成的 AGENTS/docs 命令必须改为已安装 runtime，例如 `python <codex-home>/skills/agents-md-generator/scripts/manage_docs.py ...`。
- 不要为了让这些命令可执行而把 `agents-md-generator` 的脚本复制到目标工作区自己的 `scripts/`、`skills/<name>/scripts/` 或其他项目内目录。目标项目自己的 `scripts/` 只放该项目自己的业务/工具脚本。

## Extract

```bash
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project --kind skill
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project --kind engineering
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project --start
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project --start-takeover
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project --resume
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project --resume-takeover
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project --answer-file partial.json
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project --reset-interview
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project --answers answers.json
python skills/agents-md-generator/scripts/collect_design_profile.py /path/to/project --answers answers.json --write
python skills/agents-md-generator/scripts/manage_docs.py sync-root-agents /path/to/project --write --mark-verified
python skills/agents-md-generator/scripts/select_engineering_rules.py --list
python skills/agents-md-generator/scripts/select_engineering_rules.py --task refactor --mode mini --scope on-demand
python skills/agents-md-generator/scripts/extract_commands.py /path/to/project
python skills/agents-md-generator/scripts/extract_context.py /path/to/project
```

`collect_design_profile.py --start` creates `.agents/design-interview-state.json` and returns only the current question group. Missing root `AGENTS.md` files or missing version metadata must stay on the full grouped interview. `--start` should switch into takeover mode automatically only when the current work folder already has landed content and the root `AGENTS.md` is version-mismatched against the installed `agents-md-generator`. `--start-takeover` and `--resume-takeover` expose that compatibility mode explicitly. `--resume` restores the unfinished group instead of silently restarting. `--intent read_only` marks the interview as explanation/analysis/planning/read-only review only; `--intent write` keeps the existing write path and remains the default for backward compatibility. `--answer-file partial.json` accepts answers for only the current group, then advances to group confirmation, the next group, the `extra_requirements` supplement question, final `alignment_confirmed` confirmation, the read-only completion state, subagent `design_review`, or review rework. If an unfinished interview exists, starting a new one must return `resume_required` until the caller resumes it or explicitly abandons it with `--reset-interview`. Skill and engineering interviews both require the structured directory-contract group so local structure, remote structure, future feature placement, remote conda placement, and remote runtime archive rules are always confirmed even for new projects.

The legacy no-flag and `--kind` forms still emit flat question lists for compatibility and debugging, but the supported interactive workflow is the grouped `--start` / `--resume` / `--answer-file` protocol. Takeover mode is the exception for version-mismatched old workspaces only: after the minimum confirmation fields are answered, the script auto-synthesizes the remaining strong-control answers instead of continuing into the full skill/engineering question tree, but it still must ask `extra_requirements` and require final alignment. Read-only intent must stop at `completed_read_only`, retain `answers_snapshot` plus `profile_preview`, and must not generate `design_review_request` until the caller explicitly runs `--enter-write-review`. With `--answers`, the script still validates a full answer set and produces a normalized control profile plus `review_summary`, `confirmed_so_far`, and `confirmation_question`. With `--write`, it writes `.agents/agents-control.json` and scaffolds the `docs/` governance tree only when `alignment_confirmed=true`, explicit `use_remote_server` and `extra_requirements` are present, and `design_review` is an approved subagent review with matching `reviewed_answers_hash` and `reviewed_profile_hash`.

Optional book-derived engineering rule fields are `engineering_rule_primary`, `engineering_rule_mode`, `engineering_rule_scope`, and `engineering_rule_notes`. Engineering interviews now ask them explicitly in their own groups. Use exactly one primary rule set. `mini` and `nano` are allowed modes; `full` is rejected for generated AGENTS.md output and stays reference-only. Scope must be `project-baseline`, `scoped`, or `on-demand`.

Skill development profiles require `trigger_scenarios`, `skill_design_patterns`, `resource_plan`, `progressive_disclosure_policy`, `validation_gates`, `forward_testing_policy`, `development_requirements`, `expected_outcome`, `validation_method`, and `validation_granularity`. Engineering development profiles now require the parallel engineering set: `development_requirements`, `resource_plan`, `validation_method`, `validation_granularity`, `forward_testing_policy`, and the engineering-rule answers. These fields render the strong-control profile and are verified before strong-control projects can be written. User-developed Skills must use `skills/<skill-name>/SKILL.md`; `SKILL.md` frontmatter `name` must match the folder name and use only lowercase letters, digits, and hyphens. Root-level self-hosted skill folders are invalid. When `has_existing_work=yes`, the expected `skills/<skill-name>/SKILL.md` must already exist on disk; an answer string alone is not enough. Trigger scenarios for this skill must explicitly treat current-workspace/current-repository/current-work-folder requests containing `计划`, `规划`, or `准备` as a root `AGENTS.md` check entry. If that root-check trigger finds a healthy root file, the skill should only report that the check passed. Explicit AGENTS.md / agent-rules / scoped-AGENTS requests should continue into the full design or update flow even when the root file is healthy. If the root file is missing, missing `agents_version`, or missing `generator_version`, the skill should report the exact abnormal reason and continue with the full grouped interview. Only version-mismatched old workspaces with landed content may auto-route into takeover mode. If the workspace already has landed content but still lacks a root `AGENTS.md`, the bootstrap path should read only exact-cwd Codex sessions and use them to initialize `docs/experience/history_experience/` plus the latest current `docs/experience/*.md`.

`select_engineering_rules.py` lists supported book-derived rule sets, recommends a primary rule set for task types such as `legacy`, `refactor`, `reliability`, `domain`, `data`, and `architecture`, rejects `full` for AGENTS.md output, and reports known equal-active conflicts or overlaps before those answers are written into the control profile.

`extract_commands.py` extracts candidate commands from Makefile, package.json, pyproject.toml, composer.json, go.mod, and GitHub Actions workflow `run:` lines. Commands are candidates, not verified execution results.

`extract_context.py` extracts docs, ADRs, utilities, quality configs, platform files, IDE/editor settings, architecture/ownership files, dependency automation configs, hook configs, GitHub settings/rulesets, reference projects, directory coverage candidates, agent configs, golden sample candidates, and CI rules for template sections that should point to existing files instead of copying prose.

## Token Review

```bash
python skills/agents-md-generator/scripts/codex_token_usage_review.py --hours 48
python skills/agents-md-generator/scripts/codex_token_usage_review.py --hours 48 --verbose
python skills/agents-md-generator/scripts/codex_token_usage_review.py --hours 48 --json
python skills/agents-md-generator/scripts/codex_token_usage_review.py --hours 48 --sessions-root /tmp/codex/sessions
```

`codex_token_usage_review.py` is a read-only helper for Codex local session token statistics. 只在用户明确要求进行 Codex Token 用量统计时调用；generic cost, optimization, or session-health questions do not trigger this path. The script summarizes local `event_msg -> token_count -> info.last_token_usage` rows across `*.jsonl` files under the effective sessions root. Default text output shows totals only, `--verbose` adds per-file detail, and `TotalTokens` renders as `精确值 (≈x.xx亿)`.

This command 仅在当前环境可解析到 `$CODEX_HOME/sessions` 或 `~/.codex/sessions` 且目录存在时执行. If that Codex root is missing, the script returns `ok=false` with reason `codex_sessions_not_found` in JSON mode and prints a refusal message in text mode. `--sessions-root` is only for tests or diagnostics; it does not bypass the Codex environment guard, and it must stay equal to or under the active Codex sessions root. Requests outside that tree fail with `sessions_root_outside_codex_root`.

## Render

```bash
python skills/agents-md-generator/scripts/render_agents.py /path/to/project
python skills/agents-md-generator/scripts/render_agents.py /path/to/project --profile /path/to/project/.agents/agents-control.json
python skills/agents-md-generator/scripts/render_agents.py /path/to/project --write
python skills/agents-md-generator/scripts/render_agents.py /path/to/project --profile /path/to/project/.agents/agents-control.json --write --confirm-structure-fix
python skills/agents-md-generator/scripts/render_agents.py /path/to/project --profile /path/to/project/.agents/agents-control.json --write --confirm-docs-layout
python skills/agents-md-generator/scripts/render_agents.py /path/to/project --profile /path/to/project/.agents/agents-control.json --write --confirm-branch-governance
python skills/agents-md-generator/scripts/render_agents.py /path/to/project --template-dir /path/to/templates
```

Default mode is dry-run and prints the compressed root draft. `--profile` enables strong-control sections from `.agents/agents-control.json`; without it, output must say strong control is not configured. `--write` writes AGENTS.md files inside the target project, creates the local `.agents/global-rule-overrides.json` config when needed, creates the `docs/` governance tree when a profile is present, and preserves hand-written content outside generated sections. `render_agents.py` emits `## Code Comment Policy` in generated root files from `code_comment_policy` in `.agents/global-rule-overrides.json`: the root gets a compact Chinese summary, while detailed Python/C/C++/Verilog examples stay in `references/code-comment-policy.md`. The root `AGENTS.md` must stay within `16KB`; other AGENTS files do not have this hard size cap. If preserved hand-written root content breaks that limit, `--write` fails before changing files. It must not create a root-level `experience/`; all experience summaries belong under `docs/experience/` as 10 numbered files. Strong-control roots must also document the workspace-config contract: work-folder engineering config lives under `.settings/`, local private config uses `.settings/project.local.json` or `.settings/<name>.local.json`, remote workspaces use `.settings/project.remote.json` or `.settings/<name>.remote.json`, and `.settings/*.local.json` such as `.settings/server_list.local.json` must never be copied to remote servers. If structure governance is blocked for a strong-control work folder, `--write` exits before writing AGENTS.md or docs governance unless `--confirm-structure-fix` records explicit user confirmation. `--confirm-structure-fix` means “allow the conservative structure-fix attempt”; it does not bypass the gate. After the fix attempt, the command must rerun `structure-gate` and keep the write blocked if root-level file drift, directory drift, or any other structure violation remains. If branch governance is blocked for a strong-control work folder, `--write` exits before writing AGENTS.md or docs governance unless `--confirm-branch-governance` records explicit user confirmation. If docs preflight reports an ambiguous or conflicting existing `docs/` layout, `--write` exits before writing AGENTS.md or docs governance unless `--confirm-docs-layout` records explicit user confirmation. `--template-dir` is mainly for tests or deliberate template overrides; otherwise use bundled templates in `assets/templates/`. AGENTS rendering must not scan the entire templates tree: it only reads the root/scoped AGENTS templates plus, when present, the single exact matching evolution target as supplemental guidance.

`preflight` is read-only. It checks whether `docs/` is absent, already has a complete AGENTS.md governance tree, or has an ambiguous/conflicting existing layout. It returns `status`, `docs_exists`, `safe_to_scaffold`, `conflicts`, `requires_user_confirmation`, and `question`. If confirmation is required, ask the user before writing AGENTS.md or scaffolding docs governance.

`scaffold` creates `docs/handoff/`, `docs/handoff/history_handoff/`, `docs/experience/`, `docs/experience/history_experience/`, `docs/development/`, `docs/development/history_development/`, `docs/install_configuration/`, `docs/git_manager/`, and `docs/dir_manager/` including `change_reviews/` and `history_dir_manager/`. Before creating placeholders, it automatically migrates legacy governance paths such as root `experience/`, root `DEVELOPMENT.md`, root `HANDOFF.md`, and misplaced `docs/HANDOFF.md` or `docs/DEVELOPMENT.md` into the governed `docs/` layout. It also creates the latest handoff placeholder, the latest `docs/development/DEVELOPMENT.md` baseline, install and git manager baselines, dir manager baselines, and 10 numbered experience files: fixed `1-workflow.md`, `2-scripts.md`, `3-plan.md`, `4-design-ui.md`, plus project-specific `5-*.md` through `10-*.md`. Handoff naming is strict after governance exists: if `docs/handoff/` already contains renamed or extra handoff files, `scaffold` must fail instead of masking the drift by writing a new `HANDOFF.md`. Use `scaffold --bootstrap-sessions` when the workspace already has landed content but no root `AGENTS.md` and you want the same run to initialize experience from exact-cwd Codex sessions.

`bootstrap-experience` is the explicit first-governance bootstrap for existing workspaces that still lack a root `AGENTS.md`. It reads only `.codex/sessions` transcripts whose `session_meta.payload.cwd` exactly matches the current working directory, writes one `history_experience` snapshot per matched session, and then writes the latest current `docs/experience/*.md` set from those matched sessions plus the current landed file evidence. If no exact-cwd session matches exist, it still writes the latest current experience files but marks conversation context as missing instead of inventing history.

`handoff` archives the previous `docs/handoff/HANDOFF.md` to `docs/handoff/history_handoff/HANDOFF-YYYYMMDD-HHMMSS.md`, writes the new latest handoff, increments `.agents/docs-governance-state.json`, and creates an AI experience update request every five handoffs. The current agent is expected to use that request immediately in the same conversation: read the request, generate a detailed payload, and apply it before closing the work. The input JSON can include `original_plan`, `current_step`, `problems`, `resolved`, `remaining`, `next`, `verification`, `conversation_summary`, `conversation_excerpt`, and `conversation_log_path`. Conversation fields are saved under `.agents/conversation-snapshots/` so future experience updates can read the latest 10 conversation materials. If the current handoff file has been renamed or the history folder contains non-standard archive names, `handoff` must fail until `repair-handoff-names --write` restores the governed names.

`start-session` writes `.agents/active-session.json` after the current handoff is read and before task execution begins. `resume-check` compares that active session with the current `HANDOFF.md` hash and optional conversation log; an unchanged handoff with an active session is reported as an interrupted session. `resume-repair` writes a recovery handoff and clears the active session before the next request is handled. All three commands are blocked by handoff naming drift; they must not continue by assuming a renamed file is acceptable.

`repair-handoff-names --write` is the explicit, conservative repair path for governed handoff naming. It may rename exactly one current markdown candidate back to `docs/handoff/HANDOFF.md`, and it may normalize historical markdown files into `HANDOFF-YYYYMMDD-HHMMSS.md` or `HANDOFF-YYYYMMDD-HHMMSS-N.md` using `Generated at` or file mtime. It must reject ambiguous current candidates, non-markdown files, and history files that do not actually look like handoff content.

`branch-gate` checks external work folder git governance against `.agents/agents-control.json`. When git management is enabled and the branch model is `master-and-dist-release`, it blocks normal generation if the current branch is not `master`, if the local branch set is not exactly `master` and `release`, or if the worktree is dirty. Blocked results must be shown to the user and routed into branch cleanup or release governance handling before AGENTS generation continues.
Blocked branch results include `decision_request`, `classified_reasons`, and `cleanup_plan` so callers can present a consistent confirmation prompt without parsing prose.

`work-folder-gate` aggregates the non-mutating workspace gates that usually precede confidence-sensitive work: `resume-check`, `structure-gate`, dir-manager verification, `branch-gate`, version alignment, and `check_freshness.py`. `--mode release` also requires a resolved skill directory. It reports active-session state under `resume_check` and `resume_policy`, but does not block the current in-progress session solely because `start-session` has been recorded; starting a new task must still run `resume-check` directly and repair interrupted work first. It emits `ok`, `errors`, and each component payload under stable keys so release and confidence gates can reuse the same evidence.

When git management is enabled, the generated Release Contract and git-manager guidance must explicitly forbid repointing the repository with `git config core.worktree`. That pattern is considered unsafe for this skill because it can silently desynchronize repository state; prefer normal checkout/merge or explicit `git worktree` commands instead.

`manage_dirs.py structure-gate` is the directory equivalent. It checks the enforced `primary_project_root`, allowed top-level roots, the fixed root-level file whitelist, and current structure drift without mutating the repository. It also treats `.settings/` as the governed work-folder config root and rejects `project.local.json`, `project.remote.json`, `server_list.local.json`, or any similar `*.local.json` / `*.remote.json` workspace config that appears outside `.settings/`. Root-level work artifacts such as `tests/`, `smoke/`, `smoke-*`, `reports/`, and `runs/` are optional work-folder-root directories only: they may exist at the root, but `structure-gate` must block them if they appear under `skills/<skill-name>/...` or `engineering/<project-name>/...`. If blocked during a normal design flow, the caller must ask whether to normalize the structure first; the recommended default is yes. Blocked structure results include `decision_request` with kind `structure_normalization`. `apply-structure-fix` performs only the conservative, explicit structure moves that were confirmed. `takeover-fix` is the forced local reorganization path for old workspaces already entering takeover mode; it reorganizes the local work folder under the governed primary project root, archives prior dir-manager state when present, and refreshes the structure plan afterward.

`experience` without `--payload` does not write lessons. It writes `.agents/experience-update-request.json` when a new five-handoff cadence checkpoint is due, or immediately with `--force`. The request includes project facts, current and historical handoffs, the current five-handoff window, the recent conversation window, current and historical experience files, target filenames, topic-specific detail requirements, and up to 10 recent conversation snapshots. If no conversation material exists, it sets `conversation_context_missing=true` instead of pretending the context is complete. When the checkpoint is also the tenth-handoff boundary, the same request is enriched with `requires_atomic_evolution`, a normalized `evolution_target`, `target_schema_label`, `flow_requirements`, `mixed_content_risks`, `requires_extra_evolution_review`, `review_scope`, `review_blocking`, `review_contract`, `release_alignment_evidence`, `payload_schema.evolution_summary`, and `evolution_sink` so an external Codex/agent can generate one atomic experience-plus-evolution payload without probing `evolve` first. The sink resolves to `owner-local`, `installed-sink`, or `export-pending`.

`experience --payload experience-payload.json` applies AI-authored lessons. The payload must declare `generated_by=ai` and provide all 10 files. Every experience file must include `## Evidence Read`, `## Task Context`, `## How To Apply`, `## Problems And Risks`, `## Iterated Lessons`, and `## Next Application`; short or vague summaries are rejected because future agents must be able to understand the task, implementation path, problems, and reuse conditions from the file itself. The script validates that content is not a raw HANDOFF.md copy, not placeholder text, not highly homogeneous across files, and not topic-mismatched for files such as scripts, testing, validation, docs governance, release, installation, or directory governance. Accepted files receive standardized cadence metadata such as the covered handoff window and conversation count before they are written. Existing current experience files are moved to `docs/experience/history_experience/YYYYMMDD-HHMMSS/` before accepted payload content is written. Files `5-*.md` through `10-*.md` remain selected deterministically from project facts such as testing, validation, release, installation, docs governance, directory governance, and remote deployment.

`experience-payload.json` may also include `evolution_target`, `evolution_summary`, and `evolution_review`. `evolution_target` has `family`, `category_path`, `type_slug`, and `rationale`; when omitted, the script infers a target from `.agents/agents-control.json` and repository facts. Built-in inference covers categories such as `FPGA`, `algorithm/sort`, `agent-governance`, `docs-governance`, `web/frontend`, `backend/api`, `data/database`, and `general`, and now defaults to a reusable workflow type slug instead of a repository name. AI-provided targets are validated for family/kind compatibility, safe path segments, and non-empty rationale. When the current cadence checkpoint is also a tenth handoff, `evolution_summary` and `evolution_review` are both mandatory and payload application is atomic: the script refuses to write the new experience set unless the summary is valid enough to complete evolution in the same apply and the extra evolution review approves the target. `evolution_review` must carry `verdict`, `approved_target`, `original_target`, `evidence_read`, `session_reread_performed`, `session_reread_reason`, and `full_explanation`. `approve_with_override` may suggest a better target, but template writing stays blocked until a new payload resubmits the approved target as its own `evolution_target`. Successful payload application also clears fulfilled `.agents/experience-update-request.json` / `.agents/evolution-update-request.json` / `.agents/evolution-review-request.json` files so the repository does not keep stale pending work after the checkpoint is complete.
The extra evolution review is strict about evidence. It is an additional reviewer, not a template writer. It must check release alignment against the latest handoff window, `docs/git_manager/CHANGELOG.md`, `docs/development/DEVELOPMENT.md`, recent conversation snapshots, and any available release receipt evidence. If the review rejects the current classification, or if the review cites sessions that are not exact-cwd matches, the script writes `.agents/evolution-review-request.json` and blocks template writing.
Exact-cwd session evidence remains mandatory. If `evolution_review.evidence_read.session_ids` or `session_paths` are present, they must resolve only to `.codex/sessions` transcripts whose `session_meta.payload.cwd` exactly matches the current working directory. Neighboring or similarly named workspaces are not allowed evidence sources for the extra evolution review.
`evolution_summary` is validated at two levels. First, it must satisfy the common markdown sections. Second, it must satisfy the target category workflow schema. Skill targets such as `agent-governance` must describe repository fact inspection, rule/design alignment, script/test/verify work, and docs/release/install governance flow. Engineering targets such as `FPGA` or `algorithm` must describe the corresponding engineering execution chain. If a summary writes the correct path but carries the opposite kind's workflow language, the script rejects it as mixed-content contamination.

`evolve` writes automatic evolution templates after accepted experience passes quality checks, AI-authored `evolution_summary` content exists, and the persisted extra evolution review state is still valid. Every tenth completed handoff, payload application triggers the same flow automatically; overdue checkpoints also remain due until they are completed. The summary for `1-workflow.md`, `2-scripts.md`, `3-plan.md`, and `4-design-ui.md` must synthesize the current plus latest historical versions into sections for evidence sources, applicable scenario, distilled workflow, key decisions, common problems, non-reusable content, and application checklist. Scripts must not copy `## Iterated Lessons` directly into reusable templates, and the wrapper strips any duplicated AI-provided top-level title so generated templates keep a single H1 heading. They also must not let skill-governance workflow chains leak into engineering templates or let engineering execution chains leak into skill templates. If the summary is missing or fails quality checks, `evolve` writes `.agents/evolution-update-request.json` and refuses to write low-quality templates. If the persisted review is missing, malformed, `reject`, or points to an approved target that still differs from the persisted `last_evolution_target`, `evolve` writes `.agents/evolution-review-request.json` and refuses to write templates. When the resolved sink is `installed-sink`, outputs are written into the installed `agents-md-generator/assets/templates/evolution/...` library. When the sink is `export-pending`, outputs are written under `.agents/evolution-export/<timestamp>/` and paired with `.agents/evolution-import-request.json`; `import-evolution` later publishes that bundle into the installed skill library. If `last_evolution_target` in `.agents/docs-governance-state.json` is a legacy string path or another malformed shape, `evolve --force` repairs it by falling back to a normalized inferred target before rewriting templates. When an ordinary user work folder still contains historical mistaken local `assets/templates/evolution/` output, governance commands archive it under `docs/dir_manager/history_dir_manager/YYYYMMDD-HHMMSS/legacy-evolution/` and remove the active copy instead of continuing local evolution.

`development` keeps the latest development record at `docs/development/DEVELOPMENT.md` and archives the previous current file under `docs/development/history_development/YYYYMMDD-HHMMSS/DEVELOPMENT.md` before writing a refreshed latest record. The input JSON can include `goal`, `full_plan`, `current_status`, `completed_scope`, `remaining_scope`, `verification`, `artifacts`, `version`, `results`, `next_steps`, and `remaining_risks`. The latest record must be detailed enough to explain the complete development plan, current progress, development goal, development result, risks, and next actions without requiring the reader to reconstruct the task from chat history.

`manage_dirs.py` is the strict local and remote deployment folder gate. `init` creates `DIR_MANAGER.md`, `current_structure.json`, `planned_structure.json`, `change_reviews/`, and `history_dir_manager/`; `planned_structure.json` includes `allowed_root_files`, top-level `workspace_settings`, and `remote_deployment` with a workspace root, planned remote structure, protected remote path classes, review requirements, and `require_review_for_all_mutations=true`. Existing-work engineering projects must already live under `engineering/<project-name>/`; existing-work skill projects must already live under `skills/<skill-name>/SKILL.md`. Takeover mode is the exception: it may generate the strong-control profile before those paths exist, then use `takeover-fix` to force the local work folder into the governed shape. `review` accepts JSON such as `{"changes":[{"action":"create","path":"features"}]}` and returns `approved`, `decision`, `reasons`, `risks`, `path_classes`, `matched_rules`, `user_message`, `force_confirmation_required`, `force_override_archive_required`, `dry_run`, `review_file`, and `decision_request`. `--dry-run` performs the same review without writing a `change_reviews` record. Remote review is strict for all mutation types: source and target paths must both stay inside the governed remote plan, `.settings/*.local.json` must never enter the remote workspace, remote `.settings` json files must use `.remote.json`, destructive actions on protected remote path classes are blocked by default, verified runtime artifacts must move to backups, and unverified runtime artifacts must stay in active runs. Blocked reviews exit non-zero and must be shown to the user before any force-confirmed folder change. If the user explicitly force-confirms a blocked change, run `archive` before applying it; this preserves the old dir manager content under `docs/dir_manager/history_dir_manager/YYYYMMDD-HHMMSS/`.

Root metadata is only valid when both `agents_version` and `generator_version` exist and both match the current installed `agents-md-generator` version; otherwise the workspace should be treated as trigger-required and should ask whether to enter AGENTS/docs/workspace design or restructuring instead of silently continuing as normal. Project version alignment is separate: `version_alignment_gate` checks the root Control Profile `Version:` plus DEVELOPMENT, CHANGELOG, and GIT_MANAGER against the target project skill `VERSION`, and it must not force root metadata to that project version. If root metadata includes `default_language`, the root `AGENTS.md` must also include an explicit natural-language reply rule that binds replies to that configured language unless the user explicitly switches languages, and Plan Mode output must carry the same lock: any content inside `<proposed_plan>` must use that configured default language unless the user explicitly switches languages. `verify_agents.py` rejects managed root `AGENTS.md` files that omit or weaken the code-comment policy, including missing `code_comment_policy`, missing Python/C/C++/Verilog language rules, missing the stale-comment update rule, missing the `禁止未经明确要求的批量 AI 注释` rule, or missing the formatting rule that generated code cannot be glued together. It also rejects strong-control roots that omit the `.settings` workspace-config contract, weaken the `.settings/<name>.local.json` / `.settings/<name>.remote.json` naming rule, or fail to forbid copying `.settings/*.local.json` such as `.settings/server_list.local.json` to remote servers. For non-owner repositories it must also reject project-local governance runtime commands such as `python scripts/manage_docs.py ...` or `python skills/<project-skill>/scripts/manage_docs.py ...`; external workspaces must call the installed `agents-md-generator` runtime instead of vendoring those scripts. For source-mode self-verification of this repository before installation, use `--installed-skill-dir skills/agents-md-generator` so the command verifies against the current source tree rather than an older installed copy. For strong-control Skill projects, it also requires an exact `## Skill Design Contract` section with design patterns, resource boundaries, progressive disclosure, validation gates, and forward-testing policy. The root file must point to `.agents/global-rule-overrides.json`, that global JSON governance config must exist and validate, source-governance hard-fail extensions must respect the configured line limit, tests-only eval/smoke/fixture helpers must stay out of production paths, non-GUI project tool scripts must satisfy the fixed quartet `scripts/python/<function>/<name>.py`, `scripts/shell/<function>/<name>.sh`, `scripts/bat/<function>/<name>.bat`, and `scripts/powershell/<function>/<name>.ps1`, and root AGENTS text must not keep inlining those details once they move into config. The same config also carries long-running Python heartbeat policy. By default it skips development/reference/build trees such as `ref/`, `.git/`, `vendor/`, `dist/`, `build/`, `target/`, and `node_modules/`; use `--include-skipped` only when intentionally auditing those directories. `check_freshness.py` compares Last updated metadata with git history when available. `audit_skill.py` checks this skill's structure, frontmatter, referenced resources, Python script compilation, and the repo-local `evals/evals.json` contract including required regression cases and all five Skill design pattern coverage.

`collect_design_profile.py` treats `default_conversation_language` as a formal required input for AGENTS generation and takeover-restructure flows. `package-release` copies only the installable release subset of the skill source into `dist/<skill-name>-vX.Y.Z/`, then sanitizes the release copy only. Installable Skill releases now use a shared release-content policy: top-level release members are allowlisted, governed skill-local `evals/` may remain in the packaged tree, and development-only or work-folder-only content such as `tests/`, `test/`, `smoke*`, `_smoke_runs/`, `reports/`, `runs/`, `__pycache__/`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `*.pyc`, and `*.pyo` is forbidden anywhere in the packaged tree. The gate must also fail when the source skill contains forbidden development content, the release directory contains forbidden development content, the release directory introduces unexpected top-level entries outside the allowlist, the receipt omits or mismatches its `release_content_policy` block, undeclared diffs appear, sanitization records are missing or tampered, leftover sensitive content remains, or cross-version `dist/` artifact changes happen outside the current release target.

`install_skill.py` is a post-release install confirmation helper for skill development only. Dry-run mode emits yes/no options and defaults to skip. Repository-local `dist/` installs perform strong validation by rechecking `master`, `release`, clean-worktree state, receipt-backed sanitization evidence, and the shared release-content policy. Copied standalone release folders can install only under reduced assurance after receipt, file-hash, and release-content-policy validation. It installs only with `--write`, supports `codex` and `custom` targets, and refuses to overwrite an existing skill unless `--replace` records explicit user confirmation.
