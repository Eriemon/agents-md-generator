# Script Guide

All scripts use Python standard library only.

Governance runtime split:
- `agents-md-generator` 自己的治理脚本属于 skill runtime。owner repo 可以继续用 `python skills/agents-md-generator/scripts/...` 自举；普通外部工作区生成的 AGENTS/docs 命令必须改为已安装 runtime，例如 `python <codex-home>/skills/agents-md-generator/scripts/python/docs/manage_docs.py ...`。
- 不要为了让这些命令可执行而把 `agents-md-generator` 的脚本复制到目标工作区自己的 `scripts/`、`skills/<name>/scripts/` 或其他项目内目录。目标项目自己的 `scripts/` 只放该项目自己的业务/工具脚本。

## Extract

```bash
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project --kind skill
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project --kind engineering
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project --start
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project --start-takeover
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project --resume
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project --resume-takeover
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project --answer-file partial.json
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project --reset-interview
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project --answers answers.json
python skills/agents-md-generator/scripts/python/design/collect_design_profile.py /path/to/project --answers answers.json --write
python skills/agents-md-generator/scripts/python/docs/manage_docs.py sync-root-agents /path/to/project --write --mark-verified
python skills/agents-md-generator/scripts/python/detect/task_rating_gate.py --project /path/to/project --task-text "<user task>" --json
python skills/agents-md-generator/scripts/python/release/select_engineering_rules.py --list
python skills/agents-md-generator/scripts/python/release/select_engineering_rules.py --task refactor --mode mini --scope on-demand
python skills/agents-md-generator/scripts/python/detect/extract_commands.py /path/to/project
python skills/agents-md-generator/scripts/python/detect/extract_context.py /path/to/project
```

`collect_design_profile.py --start` creates `.agents/design-interview-state.json` and returns only the current question group. Missing root `AGENTS.md` files or missing version metadata must stay on the full grouped interview. `--start` should switch into takeover mode automatically only when the current work folder already has landed content and the root `AGENTS.md` is version-mismatched against the installed `agents-md-generator`. `--start-takeover` and `--resume-takeover` expose that compatibility mode explicitly. `--resume` restores the unfinished group instead of silently restarting. `--intent read_only` marks the interview as explanation/analysis/planning/read-only review only; `--intent write` keeps the existing write path and remains the default for backward compatibility. `--answer-file partial.json` accepts answers for only the current group, then advances to group confirmation, the next group, the `extra_requirements` supplement question, final `alignment_confirmed` confirmation, the read-only completion state, subagent `design_review`, or review rework. If an unfinished interview exists, starting a new one must return `resume_required` until the caller resumes it or explicitly abandons it with `--reset-interview`. Skill and engineering interviews both require the structured directory-contract group so local structure, remote structure, future feature placement, remote conda placement, and remote runtime archive rules are always confirmed even for new projects.

`task_rating_gate.py` is a read-only global-entry helper. It prevents token-heavy default questioning by classifying the task before asking the user for difficulty or scale. It emits `ask_user_rating`, `inferred_difficulty`, `inferred_scale`, `confidence`, `reasons`, and `recommended_actions`; user-provided difficulty or scale is respected without re-asking. Hell/nightmare or project-scale results should recommend strict planning, granularity alignment, reuse-first research, and candidate tool/library/template/open-source evidence.

The legacy no-flag and `--kind` forms still emit flat question lists for compatibility and debugging, but the supported interactive workflow is the grouped `--start` / `--resume` / `--answer-file` protocol. Takeover mode is the exception for version-mismatched old workspaces only: after the minimum confirmation fields are answered, the script auto-synthesizes the remaining strong-control answers instead of continuing into the full skill/engineering question tree, but it still must ask `extra_requirements` and require final alignment. Read-only intent must stop at `completed_read_only`, retain `answers_snapshot` plus `profile_preview`, and must not generate `design_review_request` until the caller explicitly runs `--enter-write-review`. With `--answers`, the script still validates a full answer set and produces a normalized control profile plus `review_summary`, `confirmed_so_far`, and `confirmation_question`. With `--write`, it writes `.agents/agents-control.json` and scaffolds the `docs/` governance tree only when `alignment_confirmed=true`, explicit `use_remote_server` and `extra_requirements` are present, and `design_review` is an approved subagent review with matching `reviewed_answers_hash` and `reviewed_profile_hash`.

Optional book-derived engineering rule fields are `engineering_rule_primary`, `engineering_rule_mode`, `engineering_rule_scope`, and `engineering_rule_notes`. Engineering interviews now ask them explicitly in their own groups. Use exactly one primary rule set. `mini` and `nano` are allowed modes; `full` is rejected for generated AGENTS.md output and stays reference-only. Scope must be `project-baseline`, `scoped`, or `on-demand`.

Skill development profiles require `trigger_scenarios`, `skill_design_patterns`, `resource_plan`, `progressive_disclosure_policy`, `validation_gates`, `forward_testing_policy`, `development_requirements`, `expected_outcome`, `validation_method`, and `validation_granularity`. Engineering development profiles now require the parallel engineering set: `development_requirements`, `resource_plan`, `validation_method`, `validation_granularity`, `forward_testing_policy`, and the engineering-rule answers. These fields render the strong-control profile and are verified before strong-control projects can be written. User-developed Skills must use `skills/<skill-name>/SKILL.md`; `SKILL.md` frontmatter `name` must match the folder name and use only lowercase letters, digits, and hyphens. Root-level self-hosted skill folders are invalid. When `has_existing_work=yes`, the expected `skills/<skill-name>/SKILL.md` must already exist on disk; an answer string alone is not enough. Trigger scenarios for this skill must explicitly treat current-workspace/current-repository/current-work-folder requests containing `计划`, `规划`, or `准备` as a root `AGENTS.md` check entry. If that root-check trigger finds a healthy root file, the skill should only report that the check passed. Explicit AGENTS.md / agent-rules / scoped-AGENTS requests should continue into the full design or update flow even when the root file is healthy. If the root file is missing, missing `agents_version`, or missing `generator_version`, the skill should report the exact abnormal reason and continue with the full grouped interview. Only version-mismatched old workspaces with landed content may auto-route into takeover mode. If the workspace already has landed content but still lacks a root `AGENTS.md`, the bootstrap path should read only exact-cwd Codex sessions and initialize `docs/memory/` instead of creating experience files.

`select_engineering_rules.py` lists supported book-derived rule sets, recommends a primary rule set for task types such as `legacy`, `refactor`, `reliability`, `domain`, `data`, and `architecture`, rejects `full` for AGENTS.md output, and reports known equal-active conflicts or overlaps before those answers are written into the control profile.

`sync-root-agents` is the targeted root repair path. `--write` now repairs both root metadata (`agents_version` / `generator_version`) and the managed Control Profile `Version:` line when that line exists and drifts from the target project skill `VERSION`. `--mark-verified` remains the lightweight freshness path: when versions are already aligned, it updates `Last verified` without rewriting the rest of the body.

`extract_commands.py` extracts candidate commands from Makefile, package.json, pyproject.toml, composer.json, go.mod, and GitHub Actions workflow `run:` lines. Commands are candidates, not verified execution results.

`extract_context.py` extracts docs, ADRs, utilities, quality configs, platform files, IDE/editor settings, architecture/ownership files, dependency automation configs, hook configs, GitHub settings/rulesets, reference projects, directory coverage candidates, agent configs, golden sample candidates, and CI rules for template sections that should point to existing files instead of copying prose.

## Token Review

```bash
python skills/agents-md-generator/scripts/python/detect/codex_token_usage_review.py --hours 48
python skills/agents-md-generator/scripts/python/detect/codex_token_usage_review.py --hours 48 --verbose
python skills/agents-md-generator/scripts/python/detect/codex_token_usage_review.py --hours 48 --json
python skills/agents-md-generator/scripts/python/detect/codex_token_usage_review.py --hours 48 --sessions-root <REDACTED_LOCAL_PATH>
```

`codex_token_usage_review.py` is a read-only helper for Codex local session token statistics. 只在用户明确要求进行 Codex Token 用量统计时调用；generic cost, optimization, or session-health questions do not trigger this path. The script summarizes local `event_msg -> token_count -> info.last_token_usage` rows across `*.jsonl` files under the effective sessions root. Default text output shows totals only, `--verbose` adds per-file detail, and `TotalTokens` renders as `精确值 (≈x.xx亿)`.

This command 仅在当前环境可解析到 `$CODEX_HOME/sessions` 或 `~/.codex/sessions` 且目录存在时执行. If that Codex root is missing, the script returns `ok=false` with reason `codex_sessions_not_found` in JSON mode and prints a refusal message in text mode. `--sessions-root` is only for tests or diagnostics; it does not bypass the Codex environment guard, and it must stay equal to or under the active Codex sessions root. Requests outside that tree fail with `sessions_root_outside_codex_root`.

## Render

```bash
python skills/agents-md-generator/scripts/python/render/render_agents.py /path/to/project
python skills/agents-md-generator/scripts/python/render/render_agents.py /path/to/project --profile /path/to/project/.agents/agents-control.json
python skills/agents-md-generator/scripts/python/render/render_agents.py /path/to/project --write
python skills/agents-md-generator/scripts/python/render/render_agents.py /path/to/project --profile /path/to/project/.agents/agents-control.json --write --confirm-structure-fix
python skills/agents-md-generator/scripts/python/render/render_agents.py /path/to/project --profile /path/to/project/.agents/agents-control.json --write --confirm-docs-layout
python skills/agents-md-generator/scripts/python/render/render_agents.py /path/to/project --profile /path/to/project/.agents/agents-control.json --write --confirm-branch-governance
python skills/agents-md-generator/scripts/python/render/render_agents.py /path/to/project --template-dir /path/to/templates
```

Default mode is dry-run and prints the compressed root draft. `--profile` enables strong-control sections from `.agents/agents-control.json`; without it, output must say strong control is not configured. `--write` writes AGENTS.md files inside the target project, creates the local `.agents/global-rule-overrides.json` config when needed, creates the `docs/` governance tree when a profile is present, and preserves hand-written content outside generated sections. `render_agents.py` emits Coding Behavior Baseline language skill routing from `coding_behavior.language_skill_routing` in `.agents/global-rule-overrides.json`: Python and script-family create/modify work must think first, explicitly load both readable skills, and pass both gates before continuing; Python code generation/modification/commenting/normalization keeps final ownership with `readable-python-generator`; bat/cmd, shell/bash, PowerShell, and Tcl script work keeps final ownership with `readable-script-generator`; the script route still says Python 目标继续使用 `readable-python-generator`, and script wrappers that call Python remain script targets; detailed routing notes stay in `references/coding-behavior-language-routing.md`. It also emits `## Script Output Policy` from `script_output_policy`: human-readable process messages use `> INFO: [{kind}]`, `> WARNING: [{kind}]`, or `> ERR: [{kind}]`; `Kind` values are read from JSON config rather than hard-coded in implementation; Python INFO/progress output is on by default and must support `--quiet`; machine-readable JSON, generated content, and protocol stdout are exempt. The root `AGENTS.md` must stay within `20KB`; other AGENTS files do not have this hard size cap. If preserved hand-written root content breaks that limit, `--write` fails before changing files. It must not create root-level `experience/` or governed `docs/experience/` files; memory is the long-term context mechanism. Strong-control roots must also document the workspace-config contract: work-folder engineering config lives under `.settings/`, local private config uses `.settings/project.local.json` or `.settings/<name>.local.json`, remote workspaces use `.settings/project.remote.json` or `.settings/<name>.remote.json`, and `.settings/*.local.json` such as `.settings/server_list.local.json` must never be copied to remote servers. If structure governance is blocked for a strong-control work folder, `--write` exits before writing AGENTS.md or docs governance unless `--confirm-structure-fix` records explicit user confirmation. `--confirm-structure-fix` means “allow the conservative structure-fix attempt”; it does not bypass the gate. After the fix attempt, the command must rerun `structure-gate` and keep the write blocked if root-level file drift, directory drift, or any other structure violation remains. If branch governance is blocked for a strong-control work folder, `--write` exits before writing AGENTS.md or docs governance unless `--confirm-branch-governance` records explicit user confirmation. If docs preflight reports an ambiguous or conflicting existing `docs/` layout, `--write` exits before writing AGENTS.md or docs governance unless `--confirm-docs-layout` records explicit user confirmation. `--template-dir` is mainly for tests or deliberate template overrides; otherwise use bundled templates in `assets/templates/`. `v1.0.0` 起 AGENTS 渲染不再读取任何 evolution guidance；`v1.1.0` 起也不再渲染 experience contract。

```bash
python skills/agents-md-generator/scripts/python/dirs/manage_dirs.py verify /path/to/project
```

`preflight` is read-only. It checks whether `docs/` is absent, already has a complete AGENTS.md governance tree, or has an ambiguous/conflicting existing layout. It returns `status`, `docs_exists`, `safe_to_scaffold`, `conflicts`, `requires_user_confirmation`, and `question`. If confirmation is required, ask the user before writing AGENTS.md or scaffolding docs governance.

`scaffold` creates `docs/handoff/`, `docs/handoff/history_handoff/`, `docs/development/`, `docs/development/history_development/`, `docs/install_configuration/`, `docs/git_manager/`, and `docs/dir_manager/` including `change_reviews/` and `history_dir_manager/`. It no longer creates, migrates, refreshes, or validates `docs/experience/` or root-level `experience/`; existing experience folders are unmanaged historical data. It creates the latest handoff placeholder, the latest `docs/development/DEVELOPMENT.md` baseline, install and git manager baselines, and dir manager baselines. Handoff naming is strict after governance exists: if `docs/handoff/` already contains renamed or extra handoff files, `scaffold` must fail instead of masking the drift by writing a new `HANDOFF.md`.

`memory-gate` is the read-only strong-control memory gate. It checks whether memory is enabled, whether `docs/memory/MEMORY.md`, `memory.sqlite3`, `events.jsonl`, and `summaries.md` exist, whether the SQLite schema has `source_ref`, `source_timestamp`, and `sequence`, whether the search schema includes the FTS5 table, short-term table, and supporting indexes, and whether exact-cwd Codex sessions have been bootstrapped when they exist. Missing or disabled memory returns `requires_user_authorization=true` and recommends `memory-init --confirm-create`; callers must not create memory files silently. `memory-init --confirm-create` is the explicit authorized creation path and may update `.agents/agents-control.json` with the default enabled `memory_contract`; initialization and writes also rebuild or sync the SQLite FTS5 and short-term search indexes when older memory databases are detected. `memory-bootstrap-sessions` reads only Codex sessions whose `session_meta.payload.cwd` exactly matches the project, sorts them by session timestamp, writes compact timestamped memory items, redacts secrets/private paths, writes `docs/memory/bootstrap-state.json`, and refreshes `summaries.md`. `memory-read` first queries SQLite FTS5 for terms of three or more characters, then uses the indexed short-term table for short keywords such as two-character Chinese terms, and only falls back to bounded `LIKE` matching when indexed search returns no candidates. `memory-read`, `memory-write`, `memory-compress`, and `memory-verify` operate only inside the governed memory root.

`bootstrap-experience` was removed in v1.1.0. Existing-work bootstrap must use `memory-gate`, authorized `memory-init --confirm-create` when needed, and `memory-bootstrap-sessions` for exact-cwd Codex session evidence.

`handoff` archives the previous `docs/handoff/HANDOFF.md` to `docs/handoff/history_handoff/HANDOFF-YYYYMMDD-HHMMSS.md`, writes the new latest handoff, increments `.agents/docs-governance-state.json`, writes a conversation snapshot, and appends memory when memory governance is enabled. It does not create experience update requests at the fifth, tenth, or later handoff counts. The input JSON can include `original_plan`, `current_step`, `problems`, `resolved`, `remaining`, `next`, `verification`, `conversation_summary`, `conversation_excerpt`, and `conversation_log_path`. Conversation fields are saved under `.agents/conversation-snapshots/` for audit and memory context. If the current handoff file has been renamed or the history folder contains non-standard archive names, `handoff` must fail until `repair-handoff-names --write` restores the governed names.

`start-session` writes `.agents/active-session.json` after the current handoff is read and before task execution begins. `resume-check` compares that active session with the current `HANDOFF.md` hash and optional conversation log; an unchanged handoff with an active session is reported as an interrupted session. `resume-repair` writes a recovery handoff and clears the active session before the next request is handled. All three commands are blocked by handoff naming drift; they must not continue by assuming a renamed file is acceptable.

`repair-handoff-names --write` is the explicit, conservative repair path for governed handoff naming. It may rename exactly one current markdown candidate back to `docs/handoff/HANDOFF.md`, and it may normalize historical markdown files into `HANDOFF-YYYYMMDD-HHMMSS.md` or `HANDOFF-YYYYMMDD-HHMMSS-N.md` using `Generated at` or file mtime. It must reject ambiguous current candidates, non-markdown files, and history files that do not actually look like handoff content.

`branch-gate` checks external work folder git governance against `.agents/agents-control.json`. When git management is enabled and the branch model is `master-and-dist-release`, it blocks normal generation if the current branch is not `master`, if the local branch set is not exactly `master` and `release`, or if the worktree is dirty. Blocked results must be shown to the user and routed into branch cleanup or release governance handling before AGENTS generation continues.
Blocked branch results include `decision_request`, `classified_reasons`, and `cleanup_plan` so callers can present a consistent confirmation prompt without parsing prose.

`work-folder-gate` aggregates the non-mutating workspace gates that usually precede confidence-sensitive work: `resume-check`, `structure-gate`, dir-manager verification, `branch-gate`, version alignment, and `check_freshness.py`. `--mode release` also requires a resolved skill directory. It reports active-session state under `resume_check` and `resume_policy`, but does not block the current in-progress session solely because `start-session` has been recorded; starting a new task must still run `resume-check` directly and repair interrupted work first. It emits `ok`, `errors`, and each component payload under stable keys so release and confidence gates can reuse the same evidence.

When git management is enabled, the generated Release Contract and git-manager guidance must forbid creating or using additional Git worktrees, running `git worktree add`, and repointing with `git config core.worktree`. Keep work in the current working folder and use local branches for isolation. Treat `.worktrees`, `worktrees`, `.git-worktrees`, and `git-worktrees` in the project root or its parent as blocking pollution.

`manage_dirs.py structure-gate` is the directory equivalent. It checks the enforced `primary_project_root`, allowed top-level roots, the fixed root-level file whitelist, and current structure drift without mutating the repository. It also treats `.settings/` as the governed work-folder config root and rejects `project.local.json`, `project.remote.json`, `server_list.local.json`, or any similar `*.local.json` / `*.remote.json` workspace config that appears outside `.settings/`. Root-level work artifacts such as `tests/`, `smoke/`, `smoke-*`, `reports/`, and `runs/` are optional work-folder-root directories only: they may exist at the root, but `structure-gate` must block them if they appear under `skills/<skill-name>/...` or `engineering/<project-name>/...`. If blocked during a normal design flow, the caller must ask whether to normalize the structure first; the recommended default is yes. Blocked structure results include `decision_request` with kind `structure_normalization`. `apply-structure-fix` performs only the conservative, explicit structure moves that were confirmed. `takeover-fix` is the forced local reorganization path for old workspaces already entering takeover mode; it reorganizes the local work folder under the governed primary project root, archives prior dir-manager state when present, and refreshes the structure plan afterward.

`v1.0.0` 起不再支持 evolution；`experience` and `bootstrap-experience` were removed in v1.1.0 and should return argparse `invalid choice`, matching the retired v1.0.0 evolution commands. Mutating docs-governance commands clear legacy `.agents/experience-update-request.json`, `.agents/evolution-*.json`, `.agents/evolution-export/`, and legacy experience/evolution state keys so retired capability state does not leak into future runs; they must not rewrite existing `docs/experience/` files.

`development` keeps the latest development record at `docs/development/DEVELOPMENT.md` and archives the previous current file under `docs/development/history_development/YYYYMMDD-HHMMSS/DEVELOPMENT.md` before writing a refreshed latest record. The input JSON can include `goal`, `full_plan`, `current_status`, `completed_scope`, `remaining_scope`, `verification`, `artifacts`, `version`, `results`, `next_steps`, and `remaining_risks`. The latest record must be detailed enough to explain the complete development plan, current progress, development goal, development result, risks, and next actions without requiring the reader to reconstruct the task from chat history.

`manage_dirs.py` is the strict local and remote deployment folder gate. `init` creates `DIR_MANAGER.md`, `current_structure.json`, `planned_structure.json`, `change_reviews/`, and `history_dir_manager/`; `planned_structure.json` includes `allowed_root_files`, top-level `workspace_settings`, and `remote_deployment` with a workspace root, planned remote structure, protected remote path classes, review requirements, and `require_review_for_all_mutations=true`. Existing-work engineering projects must already live under `engineering/<project-name>/`; existing-work skill projects must already live under `skills/<skill-name>/SKILL.md`. Takeover mode is the exception: it may generate the strong-control profile before those paths exist, then use `takeover-fix` to force the local work folder into the governed shape. `review` accepts JSON such as `{"changes":[{"action":"create","path":"features"}]}` and returns `approved`, `decision`, `reasons`, `risks`, `path_classes`, `matched_rules`, `user_message`, `force_confirmation_required`, `force_override_archive_required`, `dry_run`, `review_file`, and `decision_request`. `--dry-run` performs the same review without writing a `change_reviews` record. Remote review is strict for all mutation types: source and target paths must both stay inside the governed remote plan, `.settings/*.local.json` must never enter the remote workspace, remote `.settings` json files must use `.remote.json`, destructive actions on protected remote path classes are blocked by default, verified runtime artifacts must move to backups, and unverified runtime artifacts must stay in active runs. Blocked reviews exit non-zero and must be shown to the user before any force-confirmed folder change. If the user explicitly force-confirms a blocked change, run `archive` before applying it; this preserves the old dir manager content under `docs/dir_manager/history_dir_manager/YYYYMMDD-HHMMSS/`.

