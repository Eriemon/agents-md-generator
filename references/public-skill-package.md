# 公开技能包合同

任何受管理技能的源目录和版本化发布目录都必须包含以下根文件：

`VERSION`、`LICENSE`、`README.md`、`README-CN.md`、`SECURITY.md`、`pyproject.toml`、`CONTRIBUTING.md`、`CITATION.cff`，以及技能运行入口 `SKILL.md`。

## README 插图规则

- README 与 README-CN 都必须有真正说明功能的本地 PNG 插图。
- 插图至少为 1600×900，便于代码托管平台和文档镜像清晰展示。
- 功能插图禁止 SVG、Mermaid、远程图片和失效的相对路径；原有头部 shields.io 徽章可作为版本、许可和目标元数据保留。
- 插图应解释“用户输入如何经过检查、设计、渲染、复核并形成可安装发布包”，而不是堆砌流水账步骤。
- Image2 生成的 PNG 若携带 SVG/远程元数据，必须先无损重编码为干净 PNG，再进入正式源目录和 dist。

## 功能图的组成合同

- 主图是横向 16:9 的功能总览，必须让读者一眼看出技能的输入、核心处理链和可验证输出。
- 细节子图按核心能力拆分，例如事实采集、设计画像、规则生成、证据验证或发布边界；每张图都要有自己的信息重点，不能只是主图的裁剪版。
- 画面可以组合表格、关系图、代码片段、状态卡片和短标签，但文字必须服务于功能解释，不能用泛化装饰替代真实流程。
- 英文和中文图应表达相同的功能关系，允许排版和色彩有小幅调整，但不能改变语义。
- 当后续技能开发者明确提出“生成图/README 插图”需求时，本合同自动生效：先检查并复用现有资产，确实缺图时再使用 Image2/ImageGen 交付本地 PNG；禁止 SVG、Mermaid、远程功能图和仅有装饰意义的海报。

| 图类 | 必须回答的问题 | 推荐的信息组件 | 不能接受的替代物 |
| --- | --- | --- | --- |
| 主图 | 用户从哪里进入，技能做什么，最终交付什么？ | 输入卡、核心处理链、输出物、门禁或边界 | 只有标题和品牌装饰的海报 |
| 项目事实/能力图 | 技能依据哪些真实事实工作？ | 目录树、事实图谱、命令/依赖/语言信号、作用域候选 | 虚构统计、与技能无关的库存图 |
| 设计画像图 | 哪些问题和策略决定了生成结果？ | 问题卡、策略滑杆、作用域表、决策矩阵、锁定状态 | 没有语义的仪表盘装饰 |
| 规则生成图 | 规则如何继承、覆盖并保持人工边界？ | 根规则、目录规则、继承箭头、受管区块、人工区块、最小差异 | 把所有内容塞进一个不可维护的大文档 |
| 证据守门图 | 结果凭什么可以交接或被阻断？ | 输入证据、门禁卡、通过/警告/阻断、回执、失败即阻断路径 | 只显示绿色成功、不显示失败条件 |

每张图的文字都必须能在对应的技能行为、配置、命令或交付物中找到依据；生成模型出现不可控的数字、版本、路径或状态时，应改为概念标签或在清理阶段删除，不能把模型臆测当作项目事实。

源目录 README 是双语产品页唯一来源；`dist/` 和 `github/` 只接受它的完整副本。门禁由 `release_content_policy.validate_public_skill_files` 统一执行；审计、打包和 GitHub 发布 CLI 都复用该函数。缺失或不合规时流程 fail closed。
